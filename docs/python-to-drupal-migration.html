Python to Drupal Port

What it takes to rebuild the text-to-SQL chatbot as a Drupal 10 module in PHP — module by module, with the one dependency that has no PHP equivalent, and what it costs to prove the behaviour did not change.

Yes, it is possible. one hard gate first
01
Possible on Drupal 10? Yes. Nothing in the chatbot needs a language feature PHP lacks. The frontend is vanilla JS with no build step and moves across untouched; the metadata and prompts are data and copy verbatim. One dependency has no PHP equivalent — sqlglot — and it is read for three different purposes that turn out to have three different answers.
02
How long for Claude? 11–17 working sessions of writing, roughly 15–25 hours. The limit is not typing speed — it is that PHP for Drupal cannot be verified without a running Drupal site, a PostgreSQL instance and provider credentials. A human developer doing the same work is 20–30 days.
03
Same behaviour, API and CLI? Both modes are in scope and share one prompt builder, so they differ only in transport. Sameness is not asserted, it is measured: a parity harness runs both implementations against the same database and compares result rows, with a floor of 95% agreement.

The one genuine blocker

What sqlglot is actually for

It turns SQL text into a tree the code can interrogate, and three modules do that for three unrelated reasons. Lumping them together is what made the first version of this assessment wrong — separated and measured against the live system, they have three different answers and only one of them is expensive.

JobPythonIn PHPVerdict
Spot an invented column sql_semantics.py EXPLAIN returns 42703 / 42P01 naming the culprit better
Block a write safety.py Static checks plus a plan inspection, behind three layers the port never touches cheap
Remember what you are looking at context.py No substitute. A purpose-built extractor, ~300–400 lines the work

Why the database cannot supply conversation memory

The obvious idea is to stop parsing and ask PostgreSQL: EXPLAIN (VERBOSE, FORMAT JSON) plans a statement without running it. That works for catching invented names. It cannot read the query back, because the tms_* objects are views. EXPLAIN describes how the statement will execute, and through a view that is a different statement:

WantedWhat the database returned
Relation Name: tms_task_flat vf_task, vf_user__field_full_name, vf_bo_wf_mapping, vf_process, vf_role_department_list
Filter: task_sla_status = 'Delayed' a ~400-character CASE WHEN lower(task.status) = 'closed' THEN… — the expression defining that column inside the view
Group Key: assigned_user_name assigned_user.field_full_name_value

What that memory is worth, measured

The same two-turn conversation, run twice on the live system. Only the state layer differs — same model, same prompt, same database.

“show AR_YD_Suiting items”then just “how many?”
With memory 22 rows listed SELECT COUNT(*) … WHERE business_object_type = 'AR_YD_Suiting' → 22
Without memory 22 rows listed no SQL at all — “Please specify what you’d like counted”

Without it the product stops being a chatbot: every question has to be self-contained. No “how many?”, no “only the active ones”, no “sort by due date”.

Why the extractor is tractable anyway

It reads five shallow things — FROM tables, top-level AND-ed comparisons, GROUP BY columns, the ORDER BY term, LIMIT. The input is not arbitrary SQL: it is model-generated, always a single SELECT against a known handful of views, with clauses in a fixed order. And it is already allowed to fail — parse_sql_state returns empty rather than raising, because a query it cannot read “should degrade the context, not abort the conversation”. A miss costs one turn’s follow-up memory.

Measure it before building on it

Harvest 100+ real generated statements from the Python turn logs, run the extractor over them, and compare against parse_sql_state field by field. The bar is 95% on filter keys and tables, since those drive the next turn. Below that, the fallbacks are a libpg_query FFI binding or keeping Python for state reading alone. Never ship a reader that guesses: a wrong remembered filter is worse than none, because every following turn inherits it invisibly and the user sees a confidently wrong answer.

Where the port is worse

The read-only gate loses one layer of four

Asked “delete all tasks”, the running system produced no SQL at all. The model refused by itself — “This system only supports read-only SELECT queries. I can't delete data.” — so the sqlglot gate was never reached. There are four barriers, not three, and they fire in order:

#LayerSurvives the port?
0 The system prompt instructs a single read-only SELECT yes copied verbatim as a string
1 The sqlglot AST gate no rebuilt from cheaper checks
2 The tms_* views are not automatically updatable yes 55000, your schema, untouched
3 A SELECT-only role in a READ ONLY transaction yes verified: wren_ro holds ['SELECT']

The replacement for layer 1 is four cheaper checks plus a plan inspection:

  • Strip comments and string literals into a scratch copy, so WHERE name = 'DROP' passes while /* SELECT */ DELETE… does not.
  • Reject stacked statements — any ; with content after it.
  • Require the first keyword to be SELECT or WITH.
  • Reject the eighteen forbidden keywords as whole words, then reject any plan containing a ModifyTable node.

Cheaper than it first looked — but not free

The port loses one barrier of four, and it is the one that never fires in normal use because the prompt already refused. That is not a licence to be casual here: layer 0 is a request a model chooses to honour, not a boundary, and it holds only until a model version, an odd phrasing or a value in your own data reads as an instruction. Layers 2 and 3 are the actual guarantees now, which is why the plan verifies both independently and treats a failure there as a release blocker rather than a bug to triage.

Requirement: both transports

API mode is the easier of the two

One interface, one method, two implementations. Both take a finished system prompt and a finished user prompt, so a second prompt-building route cannot creep in.

CLI mode harder

proc_open with the command as an array, never a string — the user's question goes in -p, and a string command would make that a shell injection. Non-blocking reads on both pipes, because a full stderr buffer with nobody draining it deadlocks a child that can run for minutes.

The real trouble is HOME. The CLI keeps credentials in $HOME/.claude, and PHP-FPM runs as a user with no home directory — so it works for the admin who installed it and is unauthenticated for the web server.

API mode simpler

One HTTPS POST to /v1/messages through core's Guzzle client. No subprocess, no stream framing, and none of the HOME trouble. If CLI mode proves awkward to operate, this is the mode to deploy.

Prompt caching is mandatory here, not an optimisation: the lean design inlines a 583-line schema into every system prompt. The CLI gets caching for free; over the API, without cache_control on the system block, that schema is re-billed on every single question.

Requirement: unchanged behaviour

How sameness gets proved

Hand-ported unit tests reproduce the assumptions of whoever ported them. A corpus does not. The parity harness runs the existing question suites through both implementations against the same database and compares result rows — two different-looking queries returning identical rows is a pass; identical-looking queries returning different rows is a failure.

CheckMethodBar
System prompt is identical diff the built prompt against the Python's, byte for byte 0 diffs
Repair layer behaves the same Pin difflib ratios before porting: actie/active 0.91, closed/closer 0.83 ±0.01
State reader agrees Same SQL through both readers; compare tables, filter keys, grouping, sorting, limit exact
Answers agree Full suites through both, result rows sorted and compared ≥ 95%
Read-only posture holds Four writes attempted against the live role; grants enumerated from information_schema all fail

The Python's own recorded figure is 114/115 on its suite. A port materially below that is a regression dressed as a migration.

Scope

What does not come across

The benchmark stays in Python. It is how accuracy is measured, it is not part of the application, and rebuilding it in PHP would double the work while producing figures that cannot be compared to the ones on record.

  • The benchmark and evaluation harness — question suites, ground truth, scoring, reporting. Keep the Python repository for measurement.
  • Metadata generation. The four metadata/*.yaml files are generated from the semantic registry on the Python side and promoted into the module as output. Change them there.
  • Wren and the MCP path. Already removed from production; the module is lean-only.
  • The retired demo database. schema.sql and seed.sql build three tables the runtime no longer queries.
  • No queue. Synchronous by decision; a question occupies one PHP-FPM worker for 5–15 seconds. Revisit above a handful of concurrent users.

Measured against the production branch: 52 files, 157 tests passing, 5 dependencies. Timings observed on this hardware — a single question answered in 5.4 s (SELECT COUNT(*) FROM tms_task_flat → 3,354) and a two-turn thread carrying its filter forward in 5.6 s.
